# LAPLACE 参考调研与讨论稿

调研日期：2026-10-12。本文件记录调研与已确认的范围；用户已确认开始实现，使用说明见 [图文概览](dashboard.md)。

## 依据与可确认范围

- 用户提供的 [控制台链接](https://chat.laplace.live/dashboard/24872476) 和截图。页面已打开，但浏览器读取连续超时，因此不声称逐项操作过该控制台的当前设置。
- [LAPLACE 官方功能介绍](https://laplace.live/chat)、[控制台说明](https://laplace.live/chat/dashboard)、[样式模板](https://laplace.live/chat/templates)、[卡片模式](https://laplace.live/chat/card-mode)、[用户历史](https://laplace.live/chat/user-history)。
- [blivedm 的消息模型](https://github.com/xfgryujk/blivedm/blob/dev/blivedm/models/web.py)。
- [消息协议采集资料](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/live/message_stream.md#弹幕-danmu_msg)。这属于社区采集的协议资料，并不是 B站官方稳定接口承诺。
- 本仓库的事件解析、展示设置和绘制代码。未运行本软件、未连接直播间，也未做性能测试。

## 主要差异

我们已有普通弹幕滚动、独立礼物/上舰、SC、互动及状态区，也有位置、外观和时间设置。
当前消息主要合成为纯文字绘制，主窗口最近事件仍是混合列表，历史上限 200 条。
缺少截图中的头像、粉丝牌、身份标识和图片表情，也缺少昵称与正文的独立排版。

参考软件区分主播阅读控制台与 OBS 输出。其控制台提供分列、已读处理、搜索及重复消息聚合。
因此，外观升级应先明确主窗口与桌面悬浮区分别采用什么阅读方式，而不只是更换字体。

## 建议优先补充

| 内容 | 建议 | 原因 |
| --- | --- | --- |
| 图文消息 | 头像、昵称、粉丝牌、舰长/房管标识、正文分开呈现 | 更接近截图，同时提高识别效率 |
| 样式预设 | 深色简约、圆角气泡、透明紧凑；单独设置昵称/正文颜色、行距、间距、背景和阴影 | 避免用户手动调很多参数才能好看 |
| B站表情 | 同时处理正文内小表情和整条图片大表情 | 当前解析阶段丢弃了相关字段 |
| 主窗口阅读 | 普通弹幕、SC、礼物分列；列宽可调整 | 避免重要信息淹没在混合列表中 |
| 未读管理 | 礼物/SC 标记已处理，筛选未读；悬浮停留时间与记录保留分开 | 卡片到期不应等同于感谢工作已完成 |
| 高流量阅读 | 相同弹幕合并计数、关键词和礼物金额过滤 | 提高可读性并控制渲染数量 |

后续可考虑按用户查看本地记录、搜索和记录导出、开播状态和时长、快捷键。
翻译、语音朗读、OBS/VTS 控制以及礼物特效属于额外工作流，需要具体使用需求后再决定范围。

## 外观建议

从截图观察：深色衬底、明亮正文、粗体昵称、彩色粉丝牌和身份标记、圆形头像，以及相对宽松的行距是主要视觉特征。
不能仅凭截图确认准确字体名称，也不能把官方模板示例中的字体当成控制台实际字体。
建议提供接近截图的默认预设，再开放字体和细节调整。

需要补充昵称与正文各自的字号、字重、颜色；头像/徽章大小及开关；正文行距、消息间距、内边距；
气泡圆角和背景不透明度；描边宽度/颜色及阴影；小表情与大表情尺寸及高度上限。
文字与背景不透明度应分别控制，避免背景调整同时把正文和头像变得难辨认。

## 表情可行性

blivedm 已将 `info[0][13]` 作为表情参数读取，可包含 URL、尺寸和动态标记；
其 `extra_dict` 解析 `info[0][15].extra`，社区消息样例中的 `emots` 字典记录了 `[热]` 等文本占位对应的图片地址和尺寸。
这些信息足以支持接收端显示图片表情，不需要增加发送弹幕功能。

实现时需同时处理对象与 JSON 字符串形式、字段缺失及格式变化。保留原始文字作为下载失败时的回退显示。
Unicode emoji 与 B站图片表情是两条不同的渲染路径，需要分别处理，不能仅靠安装一款字体解决所有表情。
动态标记不等于确定的文件格式，动图支持需按实际图片编码处理。

匿名时只展示实际下发的信息；头像、身份和 UID 缺失时降级显示，不保证能恢复完整用户资料。
匿名 UID 为 0 时不应将所有匿名观众归并为同一个用户历史。

## 保持低占用的实施方向

- 保留现有有界缓冲、批量 UI 更新和隐藏时停止刷新。
- 图像异步获取，限制并发数；同 URL 合并请求，设置内存/磁盘缓存上限及失败重试冷却。
- 只获取需要展示的资源，避免每条消息额外查用户资料或重复下载图片。
- 单条消息生成组合绘制缓存，避免每帧解码头像、表情和文本。
- 静态列表在内容变化时更新，使用控件复用/虚拟化；主窗口隐藏时暂停可视更新。
- 动态表情做独立开关，建议默认显示静态帧；启用后限制同时播放数量、帧率和尺寸，仅对可见内容播放。
- 重复消息合并优先做精确文本匹配；相似度合并是否值得增加计算量另行讨论。
- 礼物/SC 的未读记录使用单独、受控的保留策略，避免普通弹幕刷掉重要记录，也避免无限积累。

这些是设计约束，不是本版本的实测 CPU 结论。

## 已确认的决策

- 升级主窗口现有概览为类似截图的控制台：普通弹幕、SC、礼物/上舰三列，列宽可调整；进房/关注在普通弹幕列下方独立显示。
- 顶部展示房间状态及可获取的房间指标；数据缺失时显示暂无数据，不推算虚假人气或榜单。
- 桌面悬浮区继续滚动弹幕和独立事件卡片；本轮不增加悬浮聊天列表模式。
- 默认显示头像、粉丝牌、舰长/房管标识，分别提供开关；匿名资料缺失时头像占位、徽章省略。
- B站动态表情默认静态首帧，可在设置中开启动画；动画限制数量、尺寸和帧率，仅在可见时播放。
- 礼物/SC 加入未读标记与“已感谢”操作，记录独立保留且有数量上限，不随悬浮卡片过期清除。

## 已确认的实施范围

本轮先完成概览分区、图文消息、外观设置、图片表情及未读管理。
外观提供深色简约、圆角气泡、透明紧凑预设，并开放字体、字号、颜色、文字/背景透明度、间距及头像/表情尺寸。
现有悬浮区的位置、速度、刷新间隔和停留时间设置继续保留。

建议概览默认保留普通弹幕 500 条、礼物/上舰 200 条、SC 100 条、互动 100 条，分别可调且设硬上限；
数量达到上限先清理已处理记录，再按最早记录淘汰，未读数量按当前保留记录计算。
数据仅在本次运行中保留，跨次启动保存历史不属于本轮范围。

关键词/金额筛选、榜单扩展、用户历史、搜索导出、TTS 等先作为后续事项，不阻塞本轮主功能。
编译及独立目录发布后，由用户手动测试；不运行自动测试、UI 测试或直播间压测。
