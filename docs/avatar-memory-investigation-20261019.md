## 源码核对

- `DashboardSettings.ShowsAvatar` 先检查 `ShowAvatars`；普通消息卡片、进房复用控件、紧凑浮窗渲染均沿用它。关闭该项会跳过对应的消息头像控件／图片加载路径。榜单、主播资料、表情、礼物图标等其他图片不能据此称为全部停用。
- `BiliAvatarResolver.ResolveAsync` 优先接受消息自带地址；无地址且 UID 不大于零时直接返回。匿名消息是否包含这些字段由上游实际数据决定，不是“未登录必然所有事件没有头像”。
- 头像资料缓存最多 512 项，仅保存地址等小型资料；最多 16 个进行中键、2 个并发，最后一个消费者离开会取消查询。该服务的 HTTP 请求不携带账号 Cookie。
- 像素缓存正常最多 24 MiB，压力等级提高时降至 12／8／4 MiB；共享显示源的闲置预算正常最多 8 MiB／256 项，压力下继续降低。这些预算不限制整个 WinUI 进程内存，也不包含所有可见控件、位图与系统内部资源。
- `BiliImageView.ReleaseImages` 取消等待、清空 `Image.Source`、解除强引用并归还租约；共享服务随后按预算释放闲置源。`UiPixelSource.Dispose` 关闭 `SoftwareBitmapSource`；原生上传完成后再处理取消，避免上传仍在进行时提前关闭输入。
- 紧凑浮窗将图片绘入自己的行位图，行退出或换绑会释放位图并取消加载。图片已画入的标记避免因像素缓存淘汰而重复下载；该行为属于本次运行前已经存在的工作区改动，不能忽略版本变化这个变量。

源码中未发现明确的无限头像字典或缺失租约释放路径。但代码中的上限与成对释放不能证明 Windows／WinUI／GDI+ 内部资源及分配器的长期行为。

## 下一次最有区分力的验证

使用本次同一套二进制、相同房间和显示设置，每组独立重启并启用“性能诊断 → 开始记录”，回到概览保持双窗口；避免累积的进程内存跨组继承。

1. 匿名读取、关闭头像：取得当前条件的完整数量基线。
2. 已登录、仍关闭头像：与第一组比较，主要检查身份／上游数据差异。
3. 已登录、开启头像：与第二组比较，检查头像显示的增量影响。

每组至少覆盖与用户问题相近的运行时长，排除启动预热，再比较最后半小时的工作集／提交量斜率、头像绑定、解码、显示源创建释放差额及句柄。真实房间不同时段流量不同，必须同时记录事件速率；必要时用同一份隔离存档回放只切换头像开关，验证显示环节，但回放热缓存不能替代持续出现新用户的直播。

若只有第三组持续上升，头像显示链路的嫌疑才明显增强；若第二组也上升，应继续核对其他图像、富文本、历史和登录后上游字段差异。若第三组仅提高预热后平台而后段稳定，应区分正常额外工作集与持续泄漏。

## 关闭匿名读取的影响核对

| 路径 | 代码确定的行为 | 本次判断 |
|---|---|---|
| 有效身份 | `LiveAssistantViewModel.EffectiveCookies` 在匿名时返回空身份；关闭匿名且已有有效 SESSDATA 才使用运行时账号。没有有效 SESSDATA 时仍匿名 | “取消勾选匿名”和“真正账号读取”需要区分，不读取或输出凭据 |
| 弹幕连接 | `BiliProtocol` 将身份用于房间解析、签名、弹幕 token、WebSocket Cookie，以及认证 UID（匿名为 0，账号为经接口验证的 UID） | 上游可能返回不同 UID、名称、外观字段与命令负载；现有数字日志没有原始数据或逐命令字节数，不能声称已测得哪类字段增加 |
| 旧连接／轮询 | 保存有效身份变化后 `StopCoreAsync` 解绑事件，取消旧 run，等待旧资料轮询和 WebSocket 退出，再启动一组新连接；重连时旧 socket 的接收任务也被等待并释放 | 未发现按身份切换持续叠加连接／轮询的明确路径；仅代码审查，日志不能精确计数活跃连接 |
| 图像与样式 | 解析器接受头像、头像框、粉丝牌、舰长／财富身份、互动关系图标、进场背景／徽章与表情等字段。富文本可能增加 InlineUIContainer、图片控件与布局周转 | 真实字段是否因账号增加取决于上游。关闭头像不会关闭所有这些内容：互动图标、进场徽章与背景存在独立加载路径；头像框受头像及身份开关共同约束 |
| 开关关系 | 匿名选项不自动修改 `ShowAvatars`、`ShowIdentity`、`ShowMedals` 或 `AnimateEmotes` | 即使显示设置不变，上游字段变得可用也会使之前空闲的渲染路径开始工作；不能把身份切换等同于仅开启头像 |
| 头像补查 | `BiliAvatarResolver` 的资料请求不携带账号 Cookie。整段日志 requests、pending、active 始终为 0，资料缓存始终 512 | 没有额外用户资料 HTTP 查询积压证据。头像可通过消息地址下载，资料请求为零不等于没有头像图片请求 |
| 房间及榜单 | `BiliLiveInfoService`、可见的 `DashboardRankPanel` 使用有效账号 Cookie；调度频率取决于轮询／存档设置与可见性，没有账号模式专属的加速轮询分支 | 身份可能影响接口返回内容；榜单共享缓存最多 32 页，面板最多 200 人，不是无限列表 |
| 真实 UID | 可触发头像地址观察与同 UID 资料复用、重复弹幕发送者计数、礼物合并、存档身份／粉丝牌变化分析 | 方向并非全是增加：有效 UID 也能使同用户礼物更容易合并。头像资料最多 512 项、每张重复弹幕卡最多 64 个发送者、粉丝牌状态缓存最多 1,024 项 |
| 历史存档 | 入口对两种模式共用；用户识别、勋章变化分析仅在有 UID 时有额外处理，但受存档设置约束 | 本次日志写入事件累计始终 0、存档队列始终 0、SQLite 本机内存始终约 0.162 MiB，缺乏它驱动本轮增长的证据 |
| 账号同步／浏览器 | `App.xaml.cs` 启动时就启动账号同步，不由匿名开关控制；账号同步由状态变化通知驱动，没有周期性账号验证分支；取消匿名不会新建内嵌浏览器 | 诊断数字只计主程序进程，浏览器和 BrowserHost 的占用不能直接算入此日志 |

整段待处理事件数最高 8，无缓冲丢弃；557 个 UI 快照均新鲜。没有发现持续排队可以解释增长。整体托管对象范围约 10.98–26.33 MiB，不能用“字段更多”直接解释几十 MiB 的全部提交差额；图像解码、上传、绘制、富文本及系统分配器内部保留仍需按路径归因。

本次结论是：用户提供的触发条件应改为“账号读取后负载变化”，头像只是其中一条分支。下一次最有区分力的对照需固定读取身份、窗口可见性和头像／身份样式设置，并记录有效身份、开关变化以及按用途区分的图像／数据量；现有日志不能回溯补出这些字段。精确原生归因需要独立诊断进程的分配差分／调用栈，不应对当前正式进程直接套用实验修复。
