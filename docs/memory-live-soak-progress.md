# 概览与浮窗同时显示的内存优化

## 验收口径

用户已确认以任务管理器的“内存”列低于 180 MB 验收。当前用 Windows 的私有工作集对应这一常见列，仍同时报告私有提交量和总工作集。任务管理器通常以 MB 标注二进制 MiB；分析结果同时提供 180,000,000 字节和 180 MiB 两个阈值，避免混用。

停止监视、直播结束和同房再次监视保留当前内容；更换房间才清除原房间消息及资源。字体、DPI、阴影、透明度、目标帧率、消息容量和历史归档规则不降低。正式图片资产预算仍为 24 MiB，共享显示源闲置预算仍为 8 MiB／256 项。

## 已落实的修改

分支 `memory-live-soak` 基于 `room-resource-release`。提交 `65a7c71` 将概览列表改为固定的行槽位，用新消息更新已有行，避免持续插入、删除原生列表对象。普通消息、礼物、SC 和无特殊效果的进房行复用文字、徽章、头像、表情及操作按钮；媒体、大表情和特殊进房仍走原有结构。回收池每列最多 16 个，隐藏及样式变化时清理。屏幕外图片仍解除绑定与等待。

未读／感谢按钮每次绑定当前记录，回收时清空。列表保留正在阅读的记录及行内偏移，恢复滚动时等待面板提交目标可见范围。轻量容器保留系统焦点提示。共享画刷和字体只赋值、不修改，缓存数量有上限。

此前阶段已修正停止与换房语义、回收池资源释放及图片磁盘目录的重复扫描。没有强制 GC、工作集裁剪或手动 COM 释放。

## 诊断证据与限制

- 基线 `baseline-50ps` 在约 166.11 秒、7,796 条消息时首次采到私有提交量超过 350 MiB。这不是任务管理器私有工作集首次达到 350 MB 的证据，后续 dump 也会干扰内存。
- 原生容器计数显示，旧方案在 80 秒左右累计请求了 236 个普通弹幕容器，而实际只需约 8 个可见行。固定行方案使容器创建数稳定，不随每条新消息增长。
- `reading-layout-order-check` 使用原 SDK、完整显示和截图，90 秒产生 4,500 条消息。私有工作集采样峰值 163.18 MiB、私有提交量峰值 232.98 MiB。普通弹幕及 SC 的记录和行内偏移检查通过；停止、同房重启、停播保留及换房清理四项断言通过。存档 4,508 条（含系统资料事件），归档丢失及写入失败均为零。截图确认头像、徽章和表情显示。此为功能短测，不是两小时验收。
- 纯解码、纯显示源、替代 GDI 解码及 WriteableBitmap 对照未提供足以替换现有管线的改善证据，未采用这些替代实现。
- 曾试验 1.7 系列 SDK 补丁，但 MSBuild 的原生 MSIX 解压缓存导致部分短测沿用补丁 DLL；文件版本字符串不足以区分。后续构建先清理压力项目生成目录，再将两个 XAML DLL 的 SHA-256 与指定 NuGet MSIX 比对。未核对的旧短测仅作诊断，不用于精确归因。
- `cache8-diagnostic` 是只降低图片预算的替代源构建，未启动、未晋升为生产改动。

## 两小时候选

`build-stable-rows-two-hour-v1` 使用提交 `65a7c71` 对应的生产源码、原 SDK `1.7.250401001` 和 Release x64／ReadyToRun。两项原生 DLL 哈希核对通过，正式应用 Release x64 编译通过。

运行配置为概览＋浮窗同时显示，每秒 50 条、20,000 个轮换 UID、头像与透明表情、真实本地 SQLite 归档。只替换传输、图片 HTTP 和设置存储，不访问真实账号、设置或历史库。头像 URL 不同，但本地返回 8 种固定图片；不能据此证明所有实际图片格式和布局均满足目标。榜单额外网络请求关闭，使用模拟快照。默认布局、60 FPS 目标及各类显示队列沿用生产行为；悬浮拥堵省略提示单独统计，不等于历史丢失。

计划持续 7,200 秒、约 360,000 条消息。不截屏、不采 dump、不查询原生堆、不并行其他压力程序。日志约每 5 秒采样，因此峰值是观察值，不能保证采样间没有瞬时峰值。

用户随后确认“一小时数据稳定即可”，最终按一小时连续观察收尾，不再要求两小时。详细结果见 [交付说明](memory-live-soak-delivery.md)。本轮没有两小时通过结论。

首轮 `stable-rows-two-hour-v1` 在约 38 分钟后主窗口被隐藏，约 43 分钟后恢复。隐藏期间共享显示源和租约均降为零，进程私有工作集仍有波动。因此不能将这轮算作连续双窗口两小时验收，已保存 `interrupted.json` 和中断分析；隔离测试进程在确认可执行文件绝对路径后终止，模拟归档可能尚有待提交数据，不作为完整归档验收。用户确认继续完整验收后，使用相同已核对的二进制重新启动 `stable-rows-two-hour-v2`。不通过降低采样完整性或可见性要求来把中断运行判为通过。

第二轮用户确认正在使用远程桌面。系统的 Microsoft Remote Display Adapter 返回 32 Hz；现有帧时钟按屏幕刷新率限制目标至 32 FPS，实际回调约 11 次／秒。实体 NVIDIA 屏幕另有 165 Hz 模式。没有修改程序请求帧率或绕过限速逻辑；本轮结果须标为远程桌面环境，不能与首轮 60 FPS 阶段直接比较 CPU，也不能宣称实体屏幕下 60／165 FPS 已通过两小时验收。分析脚本同时输出目标帧率范围与观察到的回调频率，回调不是 GPU 实际呈现 FPS。

第二轮在 3,707.77 秒的最后采样后按用户新要求结束，共产生 184,885 条消息，连续流量采样覆盖至少 3,692.76 秒。私有工作集采样峰值 150.22 MiB、末值 140.75 MiB；私有提交量峰值 215.76 MiB、末值 206.18 MiB。第 45–60 分钟私有工作集斜率约 0.0392 MiB／分钟。两个窗口的所有流量采样均可见，最大采样间隔约 5.06 秒，每个流量采样都有帧回调；整段平均观察到约 19.47 次回调／秒。

已保存 `observation-ended.json`，没有伪造 `completed.json`。隔离进程结束前最后采样仍有 45 条待归档，因此此长观察只证明观察期间归档未报告丢失或故障，不证明退出排空或全部输入已持久化。停止保留、同房保留、停播保留及换房清理四项行为使用此前完整 `reading-layout-order-check` 的通过证据。分析命令显式带 `-ObservationSeconds 3600`，一小时内存观察通过，但 `twoHourRenderingRunCompleted` 和本轮末尾保留断言仍明确为未完成。

复现入口：`scripts/build-memory-soak.ps1`、`scripts/start-memory-soak.ps1` 和 `scripts/analyze-memory-soak.ps1`。原始模拟日志保存在忽略的 `artifacts/memory-soak/`，不随分享包交付。
