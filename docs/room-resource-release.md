# 停止监视、停播与换房的资源释放修正

## 已确认的问题及边界

- 原主动停止路径只停止网络任务、结束归档段，没有清空当前房间的消息、固定卡片、榜单和图片消费者；这些内容会一直保留到再次换房或退出。
- 原换房会清空显示内容，但图片资产、媒体资料及部分静态榜单缓存仍跨房间保留。图片资产最多 24 MiB、闲置 UI 源最多 8 MiB、媒体资料最多 128 项、榜单最多 32 页；这些是有上限的缓存，不能据此认定存在无限增长的泄漏。
- 空浮窗原来仍保留全窗口尺寸的原生画布，直到隐藏窗口或退出才销毁。其大小与区域尺寸有关，并非按消息条数增长。
- 原归档段结束后还会持有最后一份房间资料和榜单；本轮释放这些引用，不修改归档数据。

尚未通过运行日志确定用户报告的全部内存增长来源，也没有实测本版降低的内存数量。

## 本版行为

1. 主动停止后清空概览内存消息、统计曲线、榜单和悬浮内容，释放对应图片消费者；之前的真实数据仍保留在历史记录中。重新开始同一房间也使用新一轮显示资源。
2. 换房、连接失败使用同一清理入口。账号刷新、自动重连的内部停止不会清空当前消息或额外拆分历史监视段。
3. 房间资料明确从直播中（1）转为未开播（0）或轮播（2）时释放旧显示。网络断开、未知状态不当成停播。保留监视和归档，等待再次开播；停播状态不将周期榜单重新送入显示。房间资料轮询间隔决定停播识别延迟。
4. 清理时清空图片像素、头像解析、媒体资料和榜单内存缓存，并取消尚未完成的旧请求。代次检查阻止旧结果回填；榜单缓存失效真正删除旧条目。
5. WinUI 显示源仍按租约释放，不销毁仍绑定在控件上的图片。历史页、设置页等仍可见的消费者可在新代次继续加载；它们确实在使用的资源不要求归零。旧房间控件取消等待后不会自行重试。
6. 三类浮窗空白时先呈现清屏，再释放本地原生画布；下一条内容或交互示例到达后按原尺寸重建。交互编辑期间保留示例画布。
7. 退出先停止消费者，再关闭图片和媒体服务。归档待写队列按原规则提交，不为降低内存而丢弃待保存数据。

保留图片磁盘缓存、字体、DPI、阴影、透明度、目标帧率、消息容量、历史数据库与登录设置。不新增常驻清理定时器，不强制 GC、不裁剪工作集。

## 诊断字段

沿用默认关闭的资源日志开关、约 5 秒采样和现有日志上限。新增字段仅含计数和状态，不包含房间号、消息或账号。

- `roomResources.resets`：显示资源清理次数。
- `roomResources.reason`：1＝开始监视／换房，2＝主动停止／退出，3＝确认停播，4＝连接失败。
- `roomResources.offline`：最近可靠房间资料是否为未开播／轮播；停止或换房后重置。
- `images.generation`、`uiImages.generation`、`media.generation`：各缓存代次。
- `uiImages.retiredSources`、`uiImages.retiredLeases`：旧代次仍被有效控件持有的显示源／租约。

配合原有 `dashboard`、`images.items/staticPixelBytes/inflight`、`avatars`、`uiImages.sources/leases/pending`、`media.cached/inflight`、`canvasBytes/canvases` 和各浮窗位图计数判断实际释放情况。

清理后的计数下降与操作系统私有内存下降不是同一件事。托管堆、WinUI、驱动和分配器可能继续保留已分配内存；本版不承诺任务管理器数值立刻回到启动时水平。

## 用户手动验收

- 打开资源日志，在相同布局下分别监视几个主播，每轮收到图文消息后停止，等待约 20 秒，再换下一位；重复 5–10 轮。核对清理计数增加、旧浮窗消失、旧房间图片请求不回填。
- 停止后，不处于交互编辑且没有打开历史图片／其他图片页面时，概览消息、浮窗消息位图和画布应清空；旧图片与媒体请求应结束，资源计数不随换房轮数持续累计。若仍有可见主播选择头像或历史图片，相应有效租约可保留。
- 在历史图片或手动展开的媒体预览尚在加载时停止监视，确认历史内容可以继续显示，关闭／离开页面后释放。
- 主播停播后等待房间资料轮询，核对旧悬浮消息清空；再次开播能恢复弹幕与榜单。自动重连、账号刷新应保留当前内容与原监视段。
- 检查列表／卡片／滚动、交互示例、空浮窗恢复、图片透明背景及高 DPI 的显示；不应留下旧图、黑块或旧房间内容。
- 对比相近消息吞吐量下 CPU、私有内存、工作集及资源计数的走势；编译通过不能代替此项运行验证。
