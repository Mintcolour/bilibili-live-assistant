# CPU 与内存优化计划：160 MB 上限

## 1. 硬目标与统计口径

用户要求：启动约 80 MB，实际使用始终不超过初始占用的两倍，绝对上限为 160 MB。沿用已确认的任务管理器常用“内存”列口径，即私有工作集；以二进制 MiB 记录数值和原始字节，避免与私有提交量、总工作集混用。

- 定义启动基准为 `M0`，验收上限为 `B = min(160 MiB, 2 × M0)`。当前按 `M0 ≈ 80 MiB`、`B = 160 MiB` 制定方案。
- 启动基准在同一机器、同一 DPI、同一布局下，完成首页和空浮窗布局、尚未连接直播间时测量。固定启动后第 30–60 秒中位值，记录三次启动的中位结果。普通使用不为了采样而延迟连接；基准由专门验收运行取得。
- 每个发布版本公开列出基准和绝对上限，不能随运行增长自动重设初始占用；即使新版启动变为 90 MiB，上限仍为 160 MiB。
- 不以均值、末值或长时斜率替代峰值。任一有效观测超过 B 即判该场景失败。
- 工程上的常态目标为 B 的 75%–85%，当 B 为 160 MiB 时约 120–136 MiB，保留图片解码、页面恢复和消息突发余量。这是优化目标，不是当前已达到的结果。
- 私有提交量、总工作集、GC 已提交空间、系统可用内存同时保留，防止因系统换出页面而把私有工作集下降误判成资源已释放。
- App 与 BrowserHost 分别报告，不把任务移入其他进程规避 App 上限；账号登录流程不属于本轮改造范围。

160 MiB 是交付验收死线。应用缓存预算无法数学保证 Windows、WinUI、驱动和分配器全部内存；实施中必须以进程实际数据验证，超过上限则继续定位，不能宣称达标。

确认的代码开销：

- `BiliImageCache.DecodeAsync/ToStreamAsync`：压缩正文仍复制进入 WinRT 内存流，解码器资源未完整纳入应用计数。
- `DashboardList.Sync`：全局历史版本改变后，各列仍会计算数量、修订总和、数组和集合；已有稳定行槽位和可见行机制，需在此基础上增量化，不能重新全量重建。
- `MessageCard.TryRebind`、`BiliImageView.Rebind`、`ReusableMessageBody.Update`：需要区分内容变化、身份变化和纯已读状态变化，避免相同图片无必要地解绑、重绑或再次赋值。
- `OverlayWindow/FixedOverlayWindow/StationaryOverlayWindow`：同一消息的多张图片各自到达时可能多次合成位图，可在同一调度轮合并失效通知。

尚未确认：Windows 解码器、WinUI、HTTP/TLS 和原生分配器各自占差额多少。不得在未做归因前写成“已确认永久泄漏”。

## 3. 第一阶段：修正基线与资源账目

目标是让后续改动能对照，避免再靠消息条数推断内存压力。

- 固定当前分支 `runtime-image-buffers` 为优化前基线，保存启动、低频真实流量、正常双窗口及高频场景的配置摘要和数值证据，不读取 Cookie 或消息正文。
- 保留 schema 4 字段，补充图片角色、源尺寸分组、解码档位、输入缓冲在用字节、转换中像素、受控解码峰值、完整生命周期的创建／结束次数；记录聚合数量和字节，不记录 URL、UID 或昵称。
- 增加图片绑定尝试／实际更换、概览列同步／全量重算、消息位图合成／合并次数、处理耗时与分配速率，区分调用次数和实际资源创建。
- 动画的解码显示帧另行计账，不能只统计静态 `SoftwareBitmapSource` 就认为已经覆盖所有原生图片资源。
- 在隔离验收中使用独立轻量进程计量，以约 250 ms 采集私有工作集、提交量及 CPU；应用内部仍约每 5 秒采集详细资源账目。计量开销单独核对，不在 UI 线程做高频采样。
- 短时原生分配追踪只用于隔离重现归因；带追踪开销的数据不计入达标结果，不生成强制 GC 的堆快照。
- 250 ms 也不能证明不存在采样间瞬态，报告明确观测分辨率，并结合资源预留、短时峰值和实际长时日志判断，不能把有限采样说成数学保证。

阶段产物：同配置基线、分场景报告、资源账目说明与可复用对照脚本。

## 4. 第二阶段：进房头像独立开关

用户新增要求：进房可以选择不加载头像。

- 新增“显示进房头像”，默认开启，沿用“草稿即时预览、保存后应用、还原修改”。位置放在进房设置及交互浮窗的对应属性面板。
- 有效头像显示策略为全局头像开关与本类开关共同决定。由统一策略函数识别真正的进房事件；关注、点赞等共用互动事件不能误当进房，关注提示保持原设置。
- 关闭后，在概览进房列表、进房浮窗、相关预览及历史进房可见行中都不创建头像控件、不调用头像补全、不发起头像图片下载或解码。头像框依附头像一并停用，名称、粉丝牌、身份及重点提示保留。
- 当前进房消费者取消等待并释放租约；正在被其他消息共用的图片请求和显示源继续有效。头像专用区域回收宽度，不留下空白圆框。
- 网络包实际提供的头像 URL 仍正常归档，不为了补齐历史而新增网络请求。未来重新开启时仅为当时可见内容加载，不批量回填所有历史。
- 增加“不加载进房头像”场景验证，头像请求应为零；礼物、SC、普通弹幕、榜单及关注头像不受影响。

本功能提供用户选择。主目标仍需在默认头像开启时验收，不能只测关闭头像后宣称整体优化达标。

## 5. 第三阶段：减少大原图与重复解码

### 5.1 明确图片角色和物理需求

- 统一内部图片请求描述：原始规范化地址、头像／表情／装饰／封面角色、物理目标尺寸、静态／动画要求和房间代次。
- WinUI 按显示尺寸乘实际 DPI 取得物理需求，浮窗沿用物理像素规则；继续保留 64／128／256 解码档位和较大结果满足较小请求。
- 不修改事件与历史里保存的原始 URL；请求派生地址只存在于图片管线。

### 5.2 有依据地请求头像缩略图

- 仅对验证过的 B站头像 CDN 路径和后缀生成与目标档位匹配的请求，保留宽高比、透明度及必要参数；不无差别改写表情、装饰、GIF 或媒体封面。
- 未识别路径、签名参数或未知变换后缀使用原地址。缩略图请求失败时按有界规则退回原图，避免永久丢头像或无限重试。
- 覆盖 100%／150%／200% DPI、头像尺寸变化与已有 CDN 后缀，确认清晰度后才进入正式管线。

### 5.3 分开压缩正文共享与解码共享

- 相同请求地址的进行中正文下载共享；不同显示尺寸不应同时重复下载同一正文。正文只短暂交给当前解码消费者，不再增加一个常驻原图缓存。
- 解码结果继续按静态／动画和尺寸共享，保持两路下载、32 个进行中键及现有正文上限。
- 每个消费者独立取消；最后一个消费者退出时取消尚未开始的工作。换房代次和迟到结果检查沿用现有机制。
- 研究减少托管数组到 WinRT 输入流的再次复制：采用可明确释放且能断开原始数组引用的输入适配方式；必须验证 Windows 解码器在异步期间的读取需求，不能提前归还或复用正文内存。
- 解码通常保持至多两路；大原图增加有界的加权准入，避免两张大图同时制造峰值。准入不足时可取消地等待，不把队列满当作图片永久失败。
- 解码器可能使用的原生内存只能估算。大图串行及缩略图优先是控制手段，不把原图字节预算当成全部解码内存。
- 不手工释放 WinRT COM。保留 `SoftwareBitmapSource` 当前已经核对的输入所有权约定，不回退到上传结束就提前关闭底层位图的做法。
- 动画开启时，检查 `BiliImageView` 目前按整段动画保留 `BitmapImage` 的路径。紧凑编码帧仍保留现有规则，显示端改为有界的当前／下一帧资源，不随播放把最多 40 个原生显示帧全部常驻；维持最多同时播放 4 个、最高 10 FPS，并验证异步切帧、暂停及恢复。它不是本次动画关闭日志增长的解释，但必须覆盖 160 MiB 验收。

## 6. 第四阶段：概览增量更新与浮窗合成减负

### 概览和图片绑定

- `DashboardHistory` 增加各列独立版本、增量变更摘要和未读／已感谢计数；普通弹幕变化不再触发礼物、SC、互动列重复扫描。
- 新消息、礼物合并、标记已读、删除／裁剪各自维护对应统计；摘要丢失或设置变化时提供一次完整同步，不建立无界变更日志。
- `DashboardList` 保留稳定槽位、可见行、筛选、阅读锚点及行内偏移；只有受影响的已实现行需要重绑。
- 已读或感谢状态变化只更新操作区。图片地址、身份、物理尺寸及动画要求相同时保持租约，避免无意义的解绑与重新设置 `Image.Source`。
- 富文本表情槽位继续复用；相同 URL 只更新必要元数据，改变尺寸或代次时才重新申请。隐藏／重现／拖动布局后的表情恢复必须单独检查。
- 只对实际变化的文字、颜色、提示和徽章设置属性，减少 WinUI 布局和原生包装对象周转。

### 浮窗

- 每条消息图片到达后标记脏状态，同一调度轮最多合成一次；不能为了等头像而推迟已到达的表情显示。
- 滚动帧继续只移动既有位图、合并脏区域；没有内容或固定内容未变化时不触发动画时钟和重绘。
- 保留现有共享帧时钟、帧率、阴影与文字渲染，不通过降帧、降字号、降清晰度或缩短展示时间减少 CPU。
- 不增加常驻无界 GDI 位图缓存；新增复用资源必须有明确的所有者、字节计费和退出路径。

## 7. 第五阶段：常态余量与压力准入

在第三、四阶段完成对照后再调资源策略，不先粗暴缩小所有缓存。

- 当前像素资产硬上限 24 MiB、UI 闲置源 8 MiB／256 项先作为基线。试验静态／动画分类 LRU 和更小闲置预算，以命中率、重新解码次数、图片出现延迟与 CPU 共同决定；不能只看缓存字节下降。
- 给当前可见图片、进行中正文、解码转换、浮窗位图、隐藏页闲置资源分别计账，估算项与可确知的数组／位图字节分开；不重复相加共享资源。
- 采用相对于 B 的 80%／90%／95% 压力区间。当 B 为 160 MiB 时对应约 128／144／152 MiB：先回收无租约资源、降低闲置保留，再收紧非关键图片转换的并发和预留，不等待达到 160 MiB 才处理。
- 压力评估依附资源申请、释放及活动批次，合并且至多每秒一次；空闲时不持续轮询，诊断关闭后不保留额外高频监测。
- 采用恢复阈值和滞后，避免反复清缓存、重新下载导致 CPU 震荡。不得从正在显示的控件夺取租约，也不自动隐藏头像、表情或丢弃历史消息。
- 已收到的文本和存档不等待图片准入；图片等待有界并可取消。不能通过长时间不出图来伪装低内存，图片延迟同样需要验收。
- 换房取消旧代请求、释放旧显示资源；停止、停播、同房重新监视保留内容。仅文字与有上限历史保留，不要求旧房间原生图片常驻。
- SQLite 仅审计连接／命令生命周期和可见查询；先看证据，不把数据库磁盘大小当作内存，也不随意改变持久化、统计或已有历史容量。

## 8. CPU 与体验验收目标

以下为本轮工程目标，需在相同机器、功耗模式、分辨率、DPI、窗口布局和刷新率下比较。CPU 沿用按逻辑处理器数归一化的本进程百分比，不能拿 RDP 32 Hz 与本地 60／165 Hz 直接比较。

| 场景 | 目标 |
| --- | --- |
| 无消息、无动画的空闲状态 | CPU P95 不高于 0.2%，无无效帧回调或周期性重建 |
| 真实接近的普通流量 | CPU P95 以不高于 0.8% 为起点，且不高于同条件基线 |
| 50 条／秒大量消息 | 同条件 CPU P95 争取下降至少 20%；保留目标帧率与显示规则 |
| 所有状态 | 私有工作集观测峰值不超过 B，不能用 CPU 改善换取超限内存 |
| 响应和图片 | UI 延迟 P95 争取不高于 16 ms；受控网络下图片出现延迟 P95 不比基线恶化超过 10% |

CPU 百分比目标不作为降低高刷帧率的理由；当前显示条件下若未达成，单独列为未达目标。帧回调不等于实际呈现 FPS，记录回调间隔、迟帧、UI 阻塞和人工流畅度检查。

## 9. 重做验证矩阵

开发侧先做静态核对、Release x64 编译和发布文件核对；隔离运行沿用既有压力模拟授权，只操作 StressApp 和独立目录。真实 App、BrowserHost、账号和真实历史不由脚本启动或操作；真实直播由用户正常使用并回传日志。不运行额外的功能自动测试。

| 场景 | 数据与操作 | 时长／重点 |
| --- | --- | --- |
| 启动与空闲 | 固定布局，未连接，空浮窗；头像开关两种状态 | 三次基准、5 分钟空闲 |
| 真实接近的低频 | 1–5 条／秒，多用户、多格式大图，混合进房／弹幕／礼物 | 至少 1 小时；不能被高频代替 |
| 间歇流量 | 空闲、少量消息、短时 50 条／秒突发交替 | 至少 1 小时，观察原生资源回落和图片延迟 |
| 高频回归 | 50 条／秒，UID 与实际图片内容均轮换 | 至少 1 小时，比较 CPU、分配速率及峰值 |
| 生命周期 | 30 次显示／隐藏、连续多次换房、同房停启、榜单折叠与历史翻页 | 资源能回到稳定范围，不逐次累计 |
| 显示与功能 | 列表／网格／滚动、媒体、长 SC、透明表情、动画开关、DPI | 字体、图文布局、阅读位置和归档不退化 |
| 真实用户运行 | 默认头像开启、概览＋浮窗正常使用；进房头像关闭另列对照 | 至少 1 小时真实日志，作为正式达标必要证据 |

样本需包含 JPEG／PNG／WebP／GIF、64–2048 像素常见尺寸、透明图片、接近 2 MiB 的合法正文、短读／失败／取消，并覆盖大小图片混合。非法超限输入沿用已有处理，不放宽现有尺寸上限。

传输分两层验证：多格式固定素材用于可复现解码；隔离本地 HTTP 服务配合实际传输处理器覆盖流式读取、连接复用和取消。仅在隔离构建注入地址映射，不放宽生产白名单或证书验证。真实 TLS 和实际网络条件仍由真实运行日志补足。

最终至少覆盖用户实际本地刷新率；远程桌面结果单列。每项报告 M0、B、窗口状态、头像设置、帧率、消息结构、图片格式／尺寸、峰值、末值、后半小时斜率、CPU P50/P95、图片延迟和存档缺口。任何超过 B、持续增长或显示退化都不判通过。

## 10. 分批提交与交付

本次只制定计划，不实施生产代码。实施前保存干净基线，在新分支 `runtime-resource-budget` 中按以下顺序提交：

1. 修正资源账目与多格式／低频对照工具。
2. 进房头像独立开关及统一加载策略。
3. 头像尺寸请求、正文共享和解码输入生命周期。
4. 概览增量同步、避免无效图片重绑及浮窗合成合并。
5. 有依据的缓存与压力准入策略。
6. 一小时隔离与真实日志结论、发布文件核对和交付说明。

每批先短时对照，发现图片丢失、CPU 回升或资源不归零时修正该批，再继续长时验证。未解释的原生增长若仍主导占用，先完成归因，不继续堆叠无关微优化。
